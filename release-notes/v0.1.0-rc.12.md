## 发布状态

- **0.1.0-rc.12** 完善主 Bot 的自主协调：独立工作可以并行推进，补充、纠正、取消与结果交付有连续的处理流程。正式版仍为 0.0.18；本版继续供评测。

## 自主协调与并行工作

- 主 Bot 根据你的新消息判断是补充当前工作、提出独立目标，还是纠正原有方向。独立目标交给独立 Agent 执行，分别保留目标、进度和结果；主对话可以继续接收需求。
- 补充信息送给正在负责的 Agent。发现执行方向错误时，主 Bot 可以取消该任务并安排替代任务，其他工作继续推进。需要新权限或关键决定时仍提出具体问题。
- 子 Agent 可以向主 Bot 提问并收到对应答复。结果返回后，由主 Bot 核对并交付；在已有授权与成功标准内自行收下通过核验的结果，不再要求用户重复去卡片签收。
- 主 Bot 的协调回合与执行 Agent 共用有序调度。保留协调资源，使执行任务占满工作槽位时仍能接收补充、检查结果或处理取消。

## 取消、恢复与真实状态

- 区分“正在停止”“正在确认执行结果”“已取消”和“替代任务已接手”。停止过程中尚不明确的执行结果会先核实，避免重复执行可能已经完成的操作。
- 任务版本、消息归属和取消替换流程持久保存。重启后继续收尾，过期执行回执不会覆盖新任务状态，已取消的旧任务不会自行恢复。
- 回复中断与后台任务生命周期分别处理。主对话回复失败时，独立 Agent 的工作与既有结果仍保留；恢复不会把整项工作从头执行。
- 任务详情按需展示协调来源和接手关系，普通对话保持自然表达。同步中英文发布说明、用户指南、落地页与站点更新日志。

## 升级与回退

- RC4–RC11 可在“设置 → 更新与关于”通过自动或 Beta 通道检查 RC12；旧 Beta5/RC1–RC3 请下载匹配架构的安装包手动升级。
- 退出旧宿主，备份完整数据根，Desktop、CLI/TUI 与 Gateway 同步升级。npm 固定版本为 `@peer-agent/cli@0.1.0-rc.12`；归档中的 peer 与凭据助手须保持同目录。
- 回退时恢复升级前的完整备份，并另存新数据与产物。不要让旧版本直接写入新版使用过的数据目录，无需为升级重置数据。

## 验证与已知限制

- 实施阶段以真实模型验证了并行工作、补充、取消替换、重启恢复、子 Agent 提问答复和自主结果签收；此验证为实施者自审，非独立审查。核验与执行使用同一模型来源，不能视为跨供应商独立复核。
- 旧任务不会自动取得自主处置授权。原历史统计任务仍需受治理的历史查询能力和实际证据，本次协调修复不代表该任务已完成。

## Release status

- **0.1.0-rc.12** completes autonomous coordination in the main Bot: independent work can proceed concurrently, with continuous handling of additions, corrections, cancellation and result delivery. Stable remains 0.0.18; this release is for continued evaluation.

## Autonomous coordination and parallel work

- The main Bot determines whether a new message supplements current work, introduces an independent goal or corrects the direction. Independent Agents keep separate goals, progress and results while the main conversation continues receiving requests.
- Additional information reaches the responsible Agent. The main Bot can cancel work heading in the wrong direction and arrange its replacement while unrelated work continues. New permissions and essential decisions still receive specific questions.
- Child Agents can ask the main Bot questions and receive correlated answers. The main Bot checks and delivers returned results, accepting verified results within existing authorization and success criteria without asking users to sign them again in a task card.
- Short coordination turns and execution Agents share ordered scheduling with capacity reserved for coordination. Additions, result checks and cancellation remain possible when work slots are occupied.

## Cancellation, recovery and factual status

- Distinguish stopping, checking an uncertain execution outcome, cancellation and replacement handoff. Uncertain outcomes are checked before potentially completed operations can run again.
- Task versions, message ownership and cancellation/replacement transitions persist locally. Recovery finishes pending transitions; stale execution receipts cannot overwrite newer task state or revive cancelled work.
- Reply interruptions and background task lifecycles are handled separately. Independent work and existing results survive main-conversation reply failures; recovery does not restart the entire task.
- Task details reveal coordination provenance and handoffs on demand while ordinary conversation remains natural. Refresh bilingual release notes, user guidance, landing-page copy and the website changelog.

## Upgrade and rollback

- RC4–RC11 can check for RC12 through Auto or Beta in Settings → Update & About. Older Beta5/RC1–RC3 require a manual installer matching their architecture.
- Quit older hosts, back up the complete data root and upgrade Desktop, CLI/TUI and Gateway together. Use `@peer-agent/cli@0.1.0-rc.12` for a fixed npm version. Keep peer and its credential helper together.
- Roll back with the complete pre-upgrade backup while retaining new data and artifacts separately. Do not let an older version write to a directory already used by the new version. Upgrading does not require a reset.

## Validation and known limits

- Implementation acceptance used a live model for concurrent work, supplements, cancellation/replacement, restart recovery, parent/child questions and autonomous result acceptance. This is implementer self-review, not independent review. Execution and verification used the same model source, not independent cross-provider review.
- Existing tasks do not automatically gain autonomous disposition authority. The earlier history-statistics task still requires governed history access and actual evidence; coordination fixes do not establish its completion.
- Release checks cover three desktop platforms, two CLI platforms, update manifests and macOS signing and notarization. Interactive Windows/Linux installation, full screen-reader coverage, live cloud vision, complex-write Evidence and long-term use still require their corresponding acceptance. Overall readiness and GA are not declared complete.
