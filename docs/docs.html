Get started/Welcome

Welcome to Peer Agent

Peer Agent is a privacy-first local agent platform with a desktop shell and a first-class CLI (peer). Cloud models can reason; local owns capability execution, authorization, and Evidence.

What it is

Not a chat wrapper. Peer Agent is a governed executive surface: the model proposes work; the local Runtime decides whether a capability may run, executes it on your machine, and returns Evidence you can inspect.

Privacy by architecture

Files, shell, and local tools execute on your machine — not on a third-party tool server.

PermissionGrant, not polite prompts

No tool runs without an authorization decision enforced by the Runtime.

Evidence, not vibes

Capability calls return structured artifacts/logs/metadata you can audit after the fact.

One chain for every capability

Bash, files, web fetch, MCP, plugins, and skills all flow through the same governed path.

The non-negotiable chain

Capability Provider
  → Manifest
    → Runtime Projection
      → Tool Call
        → PermissionGrant
          → Evidence

This is how model intent, local execution, user authorization, and factual results stay separate and traceable.

Two first-class entries

Entry Best for Notes
Desktop Visual Thread / Workbench / Evidence review Electron shell; macOS + Windows via Releases
CLI · peer Terminal / headless sessions No Desktop required; shares ~/.peer-agent

What you can do today

  • Files — read, search, edit workspace files under scoped permissions.
  • Shell — run builds/tests/scripts; results return as inspectable artifacts.
  • Web fetch & search — pull pages/results as governed context (not hidden browsing).
  • MCP — load Model Context Protocol servers from the local registry.
  • Plugins & Skills — extend capabilities via manifests instead of patching core.

5-minute path

  1. Install Desktop from Releases or npm install -g @peer-agent/cli (Node 20+).
  2. Launch Desktop app or run peer.
  3. Configure a model provider (API key / local endpoint stays machine-side).
  4. Start a small local task (e.g. summarize git status). Approve only needed capabilities.
  5. Open Evidence / tool traces and verify what actually ran.

Get started/Desktop

Desktop workbench

Desktop is the Electron presentation shell over the same local Runtime as CLI. It is optimized for Thread reading, permission decisions, and Evidence review — not for becoming an IM bubble wall.

Layout map

RegionJob
SidebarWorkspace switcher, New Task, conversation list, settings entry
Executive ThreadDecision + execution stream for the active task
ComposerPrompt input + mode / access / model controls
WorkbenchDeeper inspection surfaces (files/previews) when needed
Evidence / tool cardsExpand what tools ran, whether authorized, and what artifacts returned

First-run checklist

  1. Open Peer Agent → choose or create a workspace (repo/folder you trust).
  2. Settings → Models / Providers → add provider + key/endpoint → set default model.
  3. Create a New Task. Prefer a low-risk prompt first (read-only inspect).
  4. When PermissionGrant UI appears, read the capability scope before approving.
  5. After the turn, expand Evidence/tool results and confirm the local side effects.

Modes you will see

  • Agent — default executive loop for doing work under permissions.
  • Plan — plan-oriented workflow; useful before high-impact edits.
  • Goal — formal goal runner with pause/resume/cancel semantics (also exposed in CLI).
Shared with CLI: conversations/settings under ~/.peer-agent. Start on Desktop, continue in peer, or the reverse.

Get started/Connect a model

Connect a model

Peer Agent is provider-flexible. Model config is local state. Keys should live in machine-side storage via the credential path, not in random project files.

Desktop

  1. Open Settings → Models / Providers.
  2. Add a provider (cloud API or local endpoint).
  3. Store the key through the app credential flow when prompted.
  4. Pick a default model + reasoning effort for new threads.
  5. Send a trivial prompt to validate connectivity before real work.

CLI

In TUI, use /model to choose model and reasoning effort, and /language if you need Chinese/English reply policy changes. Provider credentials still resolve through the same local Runtime home.

Security: do not paste long-lived keys into chat transcripts. Prefer Settings / credential helper storage.
Concepts/Local Runtime

Local Runtime

Peer Agent’s product spine is the local Capability Runtime. Desktop and CLI are shells. Capability truth is local.

Design philosophy

Local owns capability.
Interface owns expression.
Contract owns boundaries.
Evidence owns governance.

Capability chain (enforced)

Capability Provider
  → Manifest
    → Runtime Projection
      → Tool Call
        → PermissionGrant
          → Evidence
  • Provider — discovers/implements a capability family (files, shell, MCP…).
  • Manifest — declares what the capability is, not ad-hoc free text.
  • Runtime Projection — exposes model-visible tools without bypassing governance.
  • Tool Call — model intent becomes a structured call.
  • PermissionGrant — local authorization decision before execution.
  • Evidence — factual result trail (artifacts/logs/metadata), not a chat paraphrase.

Runtime stack (product view)

Electron Desktop shell  +  peer TUI shell
            \                 /
             local Runtime home (~/.peer-agent)
                      |
        Capability Runtime + Agent Runtime
                      |
     files / shell / web / MCP / plugins / skills
Hard rule: do not create separate execution paths for Bash/files/MCP/plugins that skip projection + PermissionGrant + Evidence.
Concepts/Permissions

Permissions

Authorization is a Runtime concern. Prompt text is not a grant. If there is no PermissionGrant, the capability must not execute.

Why this exists

Local agents can edit files and run shell. Without a hard permission boundary, “helpfulness” becomes unaccountable machine access. Peer Agent keeps model intent and local power separated.

Default posture: ask first

  • Sensitive writes / shell / automation should surface approval UI.
  • Prefer workspace-scoped access over machine-wide access.
  • Deny is a first-class outcome — not an error to paper over in chat.

CLI control

Use /permissions to choose the session permission policy. Re-check policy before long Goal runs that may touch many files.

Practice: grant the smallest capability set that completes the task, then revoke/relax only when Evidence shows the need.
Concepts/Evidence

Evidence

Evidence is the governance surface after execution. Peer Agent should never ask you to trust a chat summary as the only record of local side effects.

What Evidence usually contains

  • Which tool/capability ran
  • Whether it was authorized (PermissionGrant path)
  • Structured result metadata (counts, status, paths, refs)
  • Artifact references for large outputs (so the model context can stay compact)

How to use it

  1. After a turn with tools, expand Evidence/tool cards before accepting the narrative.
  2. If a write/shell call looks unexpected, stop and re-run with tighter permissions.
  3. For long Goal sessions, use Evidence as the audit trail across many steps.
Related: /compact compresses model context with a structural summary while the UI transcript can remain — Evidence/artifacts still matter more than the summary text.
Capabilities/Overview

Capabilities overview

Capabilities are declared through providers/manifests, projected to the model as tools, then executed only after PermissionGrant. There is no blessed “secret side door” for shell vs MCP vs plugins vs skills.

Area Examples Governance notes
Files read / search / edit workspace files Prefer workspace scope; writes should be reviewable via Evidence
Shell builds, tests, git, scripts High impact — keep ask-first; inspect stdout artifacts
Web fetch pages, search results as context Treat as context admission, not silent prompt injection
MCP external tools via local MCP registry Disabled servers stay non-projected until enabled
Plugins / Skills manifest-based extensions Add adapters/providers — don’t grow central host branches

Extending Peer Agent

Prefer a new Provider + Manifest path over hardcoding capabilityId branches into central hosts. That keeps Runtime Projection, permissions, and Evidence consistent as the surface grows.

Capabilities/MCP

MCP servers

MCP (Model Context Protocol) servers are loaded from Peer Agent’s local registry. Installation is not the same as enablement: a disabled server can exist without being projected as model-visible tools.

Operational flow

  1. Install/register an MCP server into the local registry.
  2. Enable it (Desktop settings/registry UI or CLI /mcp).
  3. Re-sync / inspect tools — confirm projected tool list.
  4. Run a task that needs those tools; approve PermissionGrant if prompted.
  5. Verify Evidence shows the MCP tool call and result refs.

CLI

Use /mcp to manage servers and inspect tool status without leaving the TUI.

Trust boundary: an MCP server is still a capability provider. Treat enablement like installing power tools — not like toggling a theme.
Capabilities/Skills

Skills

A Skill is a reusable instruction package for the agent — not a remote tool server. Peer Agent loads Skills from local packages (SKILL.md), manages enable/disable state, and injects selected skill context into the conversation under the same Runtime governance chain.

What a Skill is

  • Package — a folder or archive containing SKILL.md (required) plus optional assets/.
  • Frontmatter — name/description, optional whenToUse, allowed-tools, license metadata.
  • Body — the procedure / playbook the model should follow when the skill is active.
  • Local store — installed skills live under the app user-data skill root; enable/disable is persisted in local settings.
Not the same as MCP: MCP projects external tools into the Runtime. Skills primarily inject structured instruction context and optional tool-allow hints — they still cannot bypass PermissionGrant / Evidence.

Skill vs Plugin vs MCP

Object Role What you manage
Skill Reusable agent playbook / instruction package Install, enable/disable, insert/invoke into a thread
Plugin Local capability packaging & distribution unit Ship providers/adapters as packages
MCP Tool transport protocol for external tools Register/enable servers so tools can project

Package shape

my-skill/
  SKILL.md          # required (YAML frontmatter + markdown body)
  assets/           # optional attachments
  ...

Install sources currently include zip and tgz archives that contain SKILL.md at the archive root (or one top-level folder that contains it). Empty descriptions are treated as invalid noise and dropped.

Lifecycle on device

  1. Discover / install — load from local skill roots or install from zip/tgz into the user skill store.
  2. List — each skill exposes id, name, description, whenToUse, version, enabled state.
  3. Enable / disable — disabled skills remain installed but stay out of the active set.
  4. Borrow / link — optional source roots can expose available skills that can be linked into the local store.
  5. Use in a thread — insert or invoke skill context; model follows the playbook while tools still require grants.
  6. Refresh — re-scan roots / store after install or external edits.

CLI: /skill

In the TUI slash palette, /skill opens Skills management: browse installed skills, enable/disable, refresh, insert, or invoke. Desktop has the corresponding Skills UI over the same store concepts.

Action Meaning
Browse See installed skills and enabled state
Enable / disable Keep package installed while controlling participation
Refresh Reload from local roots / store
Insert Inject skill context into the current thread for the model to follow
Invoke Start using the skill as the active playbook for the next steps
Governance: enabling a Skill is not a blanket shell grant. Any tool the skill encourages still goes through Runtime Projection → PermissionGrant → Evidence.

When to use Skills

  • Repeatable workflows you want the agent to follow consistently (release checklist, review rubric, incident playbook).
  • Team conventions that should travel as packages, not as one-off prompt paste.
  • Domain procedures that should stay local and auditable, with optional tool allow-lists.

If you need a live external API tool surface, prefer MCP. If you need a new local execution provider family, prefer Plugin/Provider — not a Skill body pretending to be a tool host.

Capabilities/Plugins

Plugins

A Plugin is a local capability package — the packaging and distribution unit for local providers, adapters, optional local MCP configs, permission declarations, and install metadata. Plugins do not own cognition and are not the permission source of truth.

What a Plugin is

  • Capability package — one or more capability manifests shipped together.
  • Local adapters — how those capabilities actually run on the device (native bridge, local process, etc.).
  • Optional local MCP config — a Plugin may bundle or register local MCP servers, but MCP remains a transport, not the product object.
  • Install metadata — publisher, version, signature/trust metadata, settings/diagnostics contributions.
Plugin is not: the agent brain, a free-pass permission grant, or a cloud remote-control channel. It only declares “what I can do”; whether it runs still depends on Runtime Projection + PermissionGrant + Evidence.

Plugin vs Skill vs MCP

Object Role Not for
Plugin Local capability packaging & distribution Deciding when the agent should act; storing permission truth alone
Skill Reusable instruction / playbook package (SKILL.md) Hosting new local execution providers
MCP Tool/resource transport protocol Product object, permission model, or governance model

Still the same chain

Plugin package
  → Capability Manifest(s)
    → Runtime Projection
      → Tool Call
        → PermissionGrant
          → Local execution
            → Evidence

Any Plugin, Skill, or MCP server must enter this path. There is no blessed side door for “plugin tools” that skip projection or grants.

What a Plugin can contain

Piece Meaning
Capability manifests Declared capabilities the Runtime may project
Local adapters Native bridge / local process adapters that execute on device
Local MCP config Optional bundled local MCP server registration
Permission declarations What the package claims it needs — not the final grant
UI contributions Settings / diagnostics contribution metadata when needed

Local registration layers

Local registration is designed as three layers that must not be mixed into one folder:

  1. Built-in — first-party capabilities shipped with the client (for example Local Shell is a core provider, not a random plugin).
  2. User-installed — formal packages recorded under Electron userData plugin registry (e.g. plugins/registry.json).
  3. Workspace / dev — development-time manifests (compatibility path under workspace capabilities/*.json) for debugging, not third-party distribution.
Compat note: workspace capabilities/*.json is a development/compat entry, not the long-term home for packaged third-party plugins.

Lifecycle (product view)

  1. Install / register — package lands in the user plugin registry or a declared source root.
  2. Discover manifests — Runtime loads capability manifests from the package.
  3. Project — only projected capabilities become model-visible tools for the current workspace/session.
  4. Authorize — user PermissionGrant (or valid prior grant scope) before execution.
  5. Execute locally — adapters / local MCP run on the device.
  6. Evidence — structured results return as Evidence / ClientToolResult trail.

Local Shell is not “just a plugin”

Local Shell / Bash is a first-class high-risk built-in Capability Provider. It is modeled as core local power with command safety classification and Evidence, not as an ordinary third-party plugin toggle.

When to use a Plugin

  • You need a new local capability family (adapters/providers) packaged for install and update.
  • You want to ship local MCP + manifests + settings metadata as one distributable unit.
  • You need clear publisher/install metadata and a governed enable path on the device.

If you only need a reusable playbook, use a Skill. If you only need an external tool transport, use MCP. If you need cloud-only business APIs, that belongs to cloud MCP / cloud projection — not a local Plugin pretending to be remote control.

Help/FAQ

FAQ

Does Peer Agent upload my repo to a tool cloud?

Capability execution is local. Model providers only receive what is deliberately included in prompts/tool payloads for that turn. Use permissions + Evidence to review what left the machine boundary.

Do Desktop and CLI share history?

Yes. Both shells use the same local Runtime home under ~/.peer-agent (settings, conversations, credentials, artifacts).

Why did CLI install fail on my platform?

Today the public installer’s first-class binary archive path is macOS arm64 (peer-darwin-arm64.tar.gz). Other platforms should fail clearly in postinstall until multi-platform CLI shipping expands.

Why credentials break after I moved the binary?

Keep peer and peer-credential-helper in the same directory. The helper is not optional decoration.

What is Goal mode?

Goal is a formal runner with pause/resume/cancel and evidence-backed task completion. In CLI: /mode → Goal, then /goals, /goal-pause, /goal-resume, /goal-cancel.

Where to report bugs?

GitHub Issues on ly-ccx/Peer-Agent. Include Desktop vs CLI, version (peer --version / app version), and Evidence snippets when possible.
